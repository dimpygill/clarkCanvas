STEP 0The Problem

Why does this need to exist?

The ML project trains a model to predict student exam scores. The training data — 30 student records with study hours, sleep, attendance, and final scores — lives in an Airtable database in the cloud.

The Python script lives on a laptop. The question is: how does a Python program on a laptop reach into a database in the cloud and pull out rows of data?

The answer is the same mechanism your browser uses to load any webpage — an HTTP request. Instead of a browser asking a server for an HTML page, Python asks Airtable's server for data.

Think of Airtable as a library. The data is books. You can walk in and browse the shelves yourself (using the Airtable website). But you can also call the library on the phone, ask for a specific book, and they read it to you. The phone call is the API request. The Python requests library is the phone. The Airtable API is the library's phone number.

What the final code looks like

Here is the complete script being built in this lab. Read through it once — it won't all make sense yet. That's the point: by Step 7 every single character will be explained.

fetch_students.py — the complete script
import requests
import os

response = requests.get(
    "https://api.airtable.com/v0/appjAX8yLYxmpL971/Students",
    headers={
        "Authorization": f"Bearer {os.environ['AIRTABLE_API_KEY']}"
    }
)

print(response.status_code)
print(response.text)

data = response.json()

records = data["records"]
print(len(records))

STEP 1How the Internet Works

HTTP: the language of the web

Every time a browser loads a page, it sends an HTTP request to a server and receives an HTTP response. APIs use the exact same mechanism — just the content of the response changes (data instead of HTML).

An HTTP request has four parts. Here is the exact request the script sends to Airtable, broken apart:

Method
GET GET = "give me data, don't change anything." Other methods: POST = "create something," PATCH = "update something," DELETE = "remove something." This script reads data, so it uses GET.
URL
https://api.airtable.com/v0/appjAX8yLYxmpL971/Students The address of the specific resource. red = base ID (which database). blue = table name. Change either and you get a different (or non-existent) table.
Headers
Authorization: Bearer pat_your_token_here Extra information sent alongside the request. The Authorization header is the "membership card" — it proves this code has permission to read this base. Without it, Airtable returns 401 Unauthorized.
Body
(empty for GET requests) GET requests don't send a body — they only ask. POST and PATCH requests include a body with the data to create or update.

When Airtable receives the request, it checks the token, finds the table, and sends back an HTTP response:

Status Code
200 A 3-digit number: the server's instant verdict. 200 = success. 401 = bad token. 403 = not allowed. 404 = not found. The script prints this first so you immediately know if the request worked.
Body
{"records": [ {"id": "recXXX", "fields": {...}}, ... ]} The actual data — 30 student records in JSON format. This is what response.text prints and response.json() parses into a Python dict.

The script prints response.status_code first, before doing anything with the data. Why is this a good practice?

Printing the status code first is a debugging habit. If you skip it and the next line crashes with "KeyError: records", you don't know if the request failed (400-level status) or if the JSON structure was unexpected. 200 printed first means "the request worked, the problem is elsewhere." Non-200 means "fix the request first."

Part B — Why a virtual environment?

Python installs packages (like requests) into a shared location by default. Every project on the machine uses that same shared pile of packages. This causes two real problems:

  • Version conflicts: Project A needs requests 2.28, Project B needs requests 2.31. With one shared install, upgrading for B silently breaks A. With 10 projects this becomes unmanageable.
  • Unknown dependencies: after months of installing packages globally, nobody knows which packages this specific project actually needs. Sharing the project with someone else becomes guesswork — "it works on my machine" but not theirs.

A virtual environment (venv) solves both: it's a private, isolated copy of Python inside the project folder. Packages installed there exist only for this project. Delete the folder, and the environment is gone — the system Python is untouched.

The system Python is a shared kitchen in an apartment building — everyone's ingredients get mixed together, and someone else's expired milk breaks your recipe. A virtual environment is your own kitchenette: your ingredients, your versions, nobody else can touch them. And when the project ends, you just remove the kitchenette — the building is unaffected.

what the venv actually is — a folder structure
score-predictor/              ← the project folder
├── .venv/                    ← the virtual environment (created by python -m venv)
│   ├── Scripts/              ← Windows: activate script + python.exe live here
│   │   ├── activate          ← running this "switches on" the environment
│   │   ├── python.exe        ← a private copy of Python for this project
│   │   └── pip.exe           ← installs packages INTO this venv only
│   └── Lib/site-packages/    ← packages installed for this project (requests goes here)
└── fetch_students.py         ← the code (written in Step 8)

# On Mac/Linux the layout is .venv/bin/ instead of .venv/Scripts/
💡 What "activating" actually doesActivation is not magic — it temporarily edits the terminal's PATH so that typing python or pip uses the copies inside .venv instead of the system ones. The (.venv) prefix in the prompt is the visual confirmation. Closing the terminal ends the activation; the venv folder itself persists and can be re-activated any time.

STEP 3Airtable Setup

Setting up the API token

Airtable uses personal access tokens to control who can read or write to a base. The token is a long string (starts with pat) that proves the code's identity. Without it, every request returns 401.

Create an API token — step by step

🔑 Setup Exercise
Get a working API token in under 5 minutes
  1. Go to airtable.com/create/tokens in a browser (must be logged into Airtable). Click Create new token.
    A dialog appears with Name, Scopes, and Access fields
  2. Name it ml-lab-token (any name works — it's just a label so you remember which project it's for).
  3. Under Scopes, click Add a scope and add both:
    • data.records:read — allows reading records (needed for this lab)
    • data.records:write — allows creating records (needed for the prediction logging later)
    Both scopes appear in the list
  4. Under Access, click Add a base and select Student Score Predictor (ML Demo).
    The base appears under Access — the token is now limited to only this base
  5. Click Create token. Copy the token immediately — Airtable shows it only once.
    The token starts with pat and is a long string of letters and numbers
  6. Set the token as an environment variable in the terminal. This keeps it out of code:
    terminal — Windows
    (.venv) C:\...\score-predictor> set AIRTABLE_API_KEY=pat_PASTE_YOUR_TOKEN_HERE
    terminal — Mac/Linux
    (.venv) ~/score-predictor$ export AIRTABLE_API_KEY=pat_PASTE_YOUR_TOKEN_HERE
    Running echo %AIRTABLE_API_KEY% (Windows) or echo $AIRTABLE_API_KEY (Mac) prints the token back
    This only lasts for the current terminal session. Every time you open a new terminal, re-run the set/export command.
❌ Never paste the token directly into the .py fileCode gets shared on GitHub, screenshotted in presentations, sent in messages. Tokens inside code get exposed. Bots scan GitHub for API tokens within minutes of a commit and use them immediately. The environment variable approach keeps the token in the terminal session — invisible to anyone looking at the code files.

Why os.environ["AIRTABLE_API_KEY"] works

how Python reads the environment variable
import os

# os.environ is a dict-like object of all environment variables
token = os.environ["AIRTABLE_API_KEY"]
# → "pat_your_token_here"

# If the variable is NOT set, this crashes with KeyError:
# KeyError: 'AIRTABLE_API_KEY'
# That's a deliberate design choice — a clear error is better
# than a silent empty string that causes a confusing 401 later.

# Safer version that gives a clear default:
token = os.environ.get("AIRTABLE_API_KEY", "NOT_SET")
if token == "NOT_SET":
    print("ERROR: Set the AIRTABLE_API_KEY environment variable first")

The script crashes with KeyError: 'AIRTABLE_API_KEY' before even making the request. What is the most likely cause?

KeyError from os.environ means Python looked for "AIRTABLE_API_KEY" in the environment variables dict and didn't find it. The variable doesn't exist — it was either never set, or set in a different terminal window that's now closed. Fix: run the set/export command in this terminal, then run the script again.

The requests library in detail

requests is a third-party Python library (install with pip install requests) that makes HTTP calls simple. Without it, making an HTTP request in Python requires 30+ lines of raw socket code. With it, a GET request is one line.

without requests vs. with requests
# WITHOUT requests — 30+ lines of raw socket code
import socket, ssl
context = ssl.create_default_context()
sock = context.wrap_socket(socket.socket(), server_hostname="api.airtable.com")
sock.connect(("api.airtable.com", 443))
request = b"GET /v0/appjAX8yLYxmpL971/Students HTTP/1.1\r\nHost: ..."
# ... 25 more lines

# WITH requests — one line
response = requests.get(url, headers={...})

Understanding the headers dict

the Authorization header — broken down
headers = {
    "Authorization": f"Bearer {os.environ['AIRTABLE_API_KEY']}"
}

# What this evaluates to at runtime (assuming token is "pat_abc123"):
headers = {
    "Authorization": "Bearer pat_abc123"
}

# Breaking it down:
# "Authorization" → the header name. Airtable looks for this specific name.
# "Bearer "       → the authentication scheme. Space after Bearer is required.
# pat_abc123      → the actual token value from the environment variable.

# What Airtable checks:
# 1. Is the Authorization header present? No → 401
# 2. Is the scheme "Bearer"? No → 401
# 3. Is the token valid and not expired? No → 401
# 4. Does this token have read access to this base? No → 403
# 5. All good → 200, here is the data.

The authorization header is "Bearer pat_abc123". What is the role of the word "Bearer"?

HTTP supports multiple authentication schemes. "Bearer" means "the holder of this token is authenticated." It tells the server: what follows the space is a token string, not a username or anything else. If you omit "Bearer " (including the space), the server won't recognise the credential format and returns 401. This is a web standard — not Airtable-specific.

Attribute / MethodWhat it containsType returnedUsed for

response.text The raw response body as a string str Printing or debugging — seeing the raw JSON text Airtable sent
response.json() Parses the JSON text into a Python dict/list dict or list Actually working with the data — this is what the code uses

Why print both response.text and response.json()?

text vs json() — what's the difference
# response.text → raw string (what Airtable literally sent)
print(response.text)
'{"records":[{"id":"recABC","fields":{"Student ID":"S001",...}},...]}'

💡 Why does .json() work?response.json() is a shortcut for import json; json.loads(response.text). It takes the JSON string from the response body and converts it into native Python objects: JSON objects become dicts, JSON arrays become lists, JSON numbers become ints/floats, JSON true/false become True/False, JSON null becomes None.

STEP 6Navigating JSON

The structure of what Airtable sends back

After a successful request, response.json() returns a dict with a specific structure. Understanding this structure is essential — the data doesn't sit at the top level; it's nested three levels deep.

{ ← data = response.json() returns this dict "records": [ ← "records" key contains a list { ← each list item is one record dict "id": "recpYSiKeZTCu9ML1", ← Airtable's internal row ID "createdTime": "2026-07-21T...", ← when it was added "fields": { ← THE ACTUAL DATA IS HERE "Student ID": "S001", "Study Hours": 8, "Sleep Hours": 7, "Attendance": 0.95, "Final Score": 88 } }, { "id": "recXYZ456...", "fields": { "Student ID": "S002", "Study Hours": 2, ... } }, ... 28 more record dicts ... ] }

The key line: extracting records from the response

the last two lines of the script — explained
data = response.json()

After data = response.json() and records = data["records"], what does records[2]["fields"]["Study Hours"] return?

Reading it left to right: records[2] → the 3rd record dict (index 2) → ["fields"] → the fields dict for that student → ["Study Hours"] → the value at that key, which is 5 (student S003 studied 5 hours). This three-level navigation appears everywhere when processing Airtable API responses.

Defensive version of the script

fetch_students_safe.py — with error handling
import requests
import os

# Step 1: verify the token is set before making the request
token = os.environ.get("AIRTABLE_API_KEY")
if not token:
    print("ERROR: Set AIRTABLE_API_KEY environment variable first.")
    exit()

# Step 2: make the request
response = requests.get(
    "https://api.airtable.com/v0/appjAX8yLYxmpL971/Students",
    headers={"Authorization": f"Bearer {token}"}
)

# Step 3: check status before touching the body
print(ff"Status: {response.status_code}")
if response.status_code != 200:
    print(f"Request failed. Response: {response.text}")
    exit()

# Step 4: parse JSON (safe because we confirmed 200)
data = response.json()
records = data["records"]
print(ff"Fetched {len(records)} records")

# Step 5: inspect the first record's structure
print("\nFirst record (raw):")
print(records[0])

print("\nFirst record fields only:")
print(records[0]["fields"])

# Step 6: unwrap all records to just their fields
rows = [r["fields"] for r in records]
print(f"\nReady to use: {len(rows)} rows of student data")
print(ff"Fields available: {list(rows[0].keys())}")
