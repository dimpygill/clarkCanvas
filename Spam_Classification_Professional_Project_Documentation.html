2. Executive summary and business problem

Users receive unwanted promotional, fraudulent or otherwise unsolicited messages. Manual sorting is time-consuming; a classifier could flag potentially unwanted messages for review. This project proposes an offline prototype that predicts whether a short English-language text message is spam or not spam (ham). It will be evaluated using held-out labeled examples, with special attention to false positives (legitimate messages labeled spam) and false negatives (spam missed).

Proposed value: demonstrate the feasibility and limitations of automated triage—not claim production readiness or guarantee perfect detection.

These are proposed completion criteria, not observed results or promised accuracy. Any numerical performance threshold would need agreement after assessing the use case and baseline.

4. Project scope and boundaries

4.1 In scope (committed for the illustrative prototype)

  • One openly usable, documented, labeled English-language SMS/text dataset (subject to license and suitability checks).
  • Data inspection, label validation, duplicate review and class-balance summary.
  • Reproducible training/held-out evaluation split; avoid duplicate or near-duplicate leakageExample: 'Congratulations, you won a free iPhone' accidentally appears in both training and test sets. The model may recognize a message it already saw, making evaluation results look better than performance on genuinely new messages. Keep test data separate and check duplicates before splitting. where practical.
  • Text feature extraction (for example TF-IDF) and one baseline classifier (for example Multinomial Naive Bayes).
  • Offline inference for individual sample text messages using the trained pipeline.
  • Evaluation including confusion matrix, precision, recall, F1, and illustrative errors.
  • Simple command-line or notebook demonstration, README, and verification report.

4.2 Out of scope (explicit exclusions)

  • Connecting to real email or SMS accounts; automatic message deletion, blocking or sending.
  • Web or mobile application, hosted API, cloud deployment, live monitoring, user authentication.
  • Multilingual support, image attachments, URLs as live destinations, phishing investigation.
  • Deep-learning model training, multiple-model optimization, continuous retraining, real-time feedback loops.
  • Claims of regulatory compliance, production security certification or guaranteed spam filtering accuracy.

4.3 Future enhancements (not commitments)

Explore threshold tuning, additional models, multilingual data, a review interface, feedback collection, privacy assessment and deployment only after a separately approved change in scope.

4.4 Assumptions and constraints

  • One contributor, ordinary laptop, Python and open-source libraries; no paid services required.
  • Only lawfully shareable, appropriately licensed sample data will be used; no private messages or secrets.
  • The dataset represents a limited domain and may not generalize to current real-world email traffic.
  • Timebox is six weeks; unresolved enhancements are deferred rather than silently added.

7. Dataset and technical design

7.1 Dataset plan

Candidate: a public SMS spam dataset such as the UCI SMS Spam Collection, subject to verification of its current availability, permitted use, format and citation before adoption. The source is a candidate, not an already downloaded or inspected asset. Record actual row counts and label distribution only after inspecting the chosen data. Use anonymized or synthetic examples in screenshots when appropriate.

7.2 Proposed pipeline

Labeled messages → Validate / inspect → Split training & held-out data → Fit TF-IDF + Naive Bayes on training data → Predict held-out labels → Evaluate errors & metrics → Demo new text

Fit preprocessing only on the training partition; applying a fitted transformation to held-out text is appropriate, but fitting it on the full dataset would leak information. Save vectorizer and model together as a single pipeline. Do not interpret a sample prediction as proof of model accuracy.

14. Completion, handoff and retrospective

Before closing, verify the requirement IDs against evidence; preserve reproducible code and instructions; record unresolved defects and known limits; identify who reviewed the results. Retrospective prompts: Which assumptions were wrong? What took longer than estimated? What did the error analysis reveal? Which feature should be prioritized next and why?

15. How to adapt this professional example to the one-week AI midterm

This is the key teaching distinction: the six-week document shows how a professional individual contributor plans and controls a project. The AI midterm asks for a small, meaningful, evidence-based learning project, not a full production process. A research-and-demonstration path is also valid; students are not required to train a spam model.

15.1 Two legitimate midterm approaches using the same topic

Path A — Build: use a suitable labeled dataset to train or adapt a simple classifier, show sample predictions and a small held-out evaluation, and discuss a mistake or limitation. Only undertake this if feasible given the student's starting point.

Path B — Research and demonstrate: explain spam classification, text-to-feature transformation, labels and confusion matrix; walk through a credible existing runnable example or carefully annotated demonstration; investigate false positives/false negatives and document sources. A newly trained model is not required for this path.

15.2 What to do after finishing a scope draft early

  1. Challenge your assumptions: What data or evidence is actually available? What will count as a successful demonstration?
  2. Produce the first concrete artifact: load a small permitted dataset, run a sample, draw a workflow, or inspect an existing research demonstration.
  3. Write two verification cases: expected and possible failure/limitation; do not invent observed outcomes.
  4. Identify one blocker and a fallback: for example, if the dataset is unsuitable, use an existing documented demonstration for the research path.
  5. Update scope based on evidence: remove unrealistic features before spending the week on them.

Reflection question: “What did you discover by trying the first step that you could not have known by writing the scope alone?” This distinguishes meaningful planning from quickly filling in a template.
