Python Dictionaries: From First Principles to Real Databases

A dictionary is Python's way of storing information as labeled pairs — and, as it turns out, it's also exactly how a JSON API response and a database row look once they land in your code. This tutorial builds that idea up from scratch.

student = {"name": "Amara", "major": "Computer Science"}
key — the label you look things up by value — the data stored under that label
Level 1 · Beginner

What is a dictionary?

Think of a real dictionary: you look up a word and get its definition. A Python dictionary works the same way — you look up a key and get its value. Unlike a list, items aren't found by position (0, 1, 2…); they're found by name.

Creating a dictionary

Curly braces {} hold comma-separated key: value pairs.

student = {
    "name": "Amara",
    "age": 21,
    "major": "Computer Science"
}
print(student)
print(type(student))
Output{'name': 'Amara', 'age': 21, 'major': 'Computer Science'} <class 'dict'>

You can also build one with dict(), or from a list of pairs:

empty = {}
also_empty = dict()
from_pairs = dict([("a", 1), ("b", 2)])
via_kwargs = dict(name="Amara", age=21)
print(from_pairs)
print(via_kwargs)
Output{'a': 1, 'b': 2} {'name': 'Amara', 'age': 21}
Since Python 3.7: dictionaries remember the order you inserted items in. Older tutorials that say "dicts are unordered" are describing versions before 3.7.

Accessing values

Use square brackets with the key. If the key doesn't exist, Python raises a KeyError — so use .get() when you're not sure a key is there.

print(student["name"])
print(student.get("gpa"))
print(student.get("gpa", "N/A"))
print(student["gpa"])  # this line will crash
OutputAmara None N/A Traceback (most recent call last): KeyError: 'gpa'

.get(key, default) is the safe way to peek at a dictionary without risking a crash.

Adding and updating

Assigning to a key that doesn't exist yet creates it. Assigning to a key that already exists overwrites it. Same syntax, two behaviors — the dictionary just does whichever one applies.

student["gpa"] = 3.8       # new key -> added
student["age"] = 22         # existing key -> updated
print(student)
Output{'name': 'Amara', 'age': 22, 'major': 'Computer Science', 'gpa': 3.8}

Removing items

del student["age"]                     # removes silently
major = student.pop("major")           # removes AND returns the value
missing = student.pop("minor", "N/A")  # avoids KeyError with a default
print(major, missing)
print(student)

last_pair = student.popitem()  # removes the most-recently-inserted pair
print(last_pair)

student.clear()  # empty it out completely
print(student)
OutputComputer Science N/A {'name': 'Amara', 'gpa': 3.8} ('gpa', 3.8) {}

Checking membership & iterating

contact = {"name": "Raj", "email": "raj@example.com", "city": "Seattle"}

print("name" in contact)          # checks the KEYS
print("Raj" in contact)           # False -- not checking values
print("Raj" in contact.values())  # this is how you check values

for key in contact:
    print(key, "->", contact[key])

for key, value in contact.items():
    print(f"{key}: {value}")

print(len(contact))
OutputTrue False True name -> Raj email -> raj@example.com city -> Seattle name: Raj email: raj@example.com city: Seattle 3

.keys(), .values(), and .items() give you "view" objects — live windows onto the dictionary's keys, values, or pairs.

Level 2 · Intermediate

Nesting, comprehensions, and everyday patterns

Once the basics feel natural, dictionaries start showing up everywhere — holding other dictionaries, built in one line with comprehensions, or quietly counting things in a loop.

Nested dictionaries

A value can be anything — including another dictionary. This is how you represent structured records, like a company directory.

company = {
    "employee1": {"name": "Raj", "dept": "Engineering"},
    "employee2": {"name": "Mei", "dept": "Marketing"}
}
print(company["employee1"]["name"])
print(company["employee2"]["dept"])
OutputRaj Marketing

Useful methods: update() and setdefault()

profile = {"name": "Mei", "city": "Seattle"}
profile.update({"city": "Portland", "role": "Engineer"})
print(profile)

# setdefault: get the value if the key exists,
# otherwise set it to the default AND return that default
level = profile.setdefault("level", "Junior")
print(level)
print(profile)

# calling it again on an EXISTING key does not overwrite it
level_again = profile.setdefault("level", "Senior")
print(level_again)
Output{'name': 'Mei', 'city': 'Portland', 'role': 'Engineer'} Junior {'name': 'Mei', 'city': 'Portland', 'role': 'Engineer', 'level': 'Junior'} Junior

Dictionary comprehensions

Just like a list comprehension, but it builds key: value pairs instead of single items.

squares = {x: x**2 for x in range(1, 6)}
print(squares)

evens_only = {x: x**2 for x in range(1, 11) if x % 2 == 0}
print(evens_only)
Output{1: 1, 2: 4, 3: 9, 4: 16, 5: 25} {2: 4, 4: 16, 6: 36, 8: 64, 10: 100}

Merging dictionaries

Three ways to combine dictionaries. In every case, when both sides share a key, the later value wins.

defaults = {"theme": "light", "font_size": 12}
overrides = {"font_size": 16, "language": "en"}

merged_update = defaults.copy()
merged_update.update(overrides)

merged_unpack = {**defaults, **overrides}

merged_pipe = defaults | overrides   # Python 3.9+

print(merged_pipe)
Output{'theme': 'light', 'font_size': 16, 'language': 'en'}

Counting with defaultdict

A very common real pattern: tallying how often something occurs.

from collections import defaultdict

word_count = defaultdict(int)  # missing keys start at 0 automatically
for word in ["cat", "dog", "cat", "cat", "dog"]:
    word_count[word] += 1

print(word_count)
print(dict(word_count))
Outputdefaultdict(<class 'int'>, {'cat': 3, 'dog': 2}) {'cat': 3, 'dog': 2}

Sorting a dictionary

Dictionaries themselves don't have a .sort() method — instead, sort the .items() and rebuild a dict from the result.

scores = {"Ana": 88, "Ben": 95, "Cy": 72}

by_score_desc = dict(
    sorted(scores.items(), key=lambda item: item[1], reverse=True)
)
print(by_score_desc)
Output{'Ben': 95, 'Ana': 88, 'Cy': 72}

Level 3 · Advanced

Dictionaries as data records

This is the level where dictionaries stop being just "a Python thing" and start becoming the bridge between your code and everything outside it — APIs, files, and databases. Everything below is setup for the database examples that follow.

A list of dictionaries = a table

If one dictionary is a record, a list of dictionaries is a table: each dictionary is a row, and its keys are the column names.

students = [
    {"id": 1, "name": "Amara", "gpa": 3.8},
    {"id": 2, "name": "Raj", "gpa": 3.5},
    {"id": 3, "name": "Mei", "gpa": 3.9},
]

for row in students:
    print(row["name"], "-", row["gpa"])
OutputAmara - 3.8 Raj - 3.5 Mei - 3.9

Building a dict with zip() — remember this one

zip() pairs up two sequences item by item. Feed the result into dict() and you get a dictionary made from "column names" and "row values" — which is exactly the shape a database result comes back in.

columns = ["id", "name", "gpa"]
values = [3, "Mei", 3.9]

row = dict(zip(columns, values))
print(row)
Output{'id': 3, 'name': 'Mei', 'gpa': 3.9}
Keep this in mind: the SQL Server section later uses this exact pattern to turn database rows into dictionaries.

Unpacking a dict into a function call

def create_student(name, gpa, major="Undeclared"):
    return {"name": name, "gpa": gpa, "major": major}

info = {"name": "Kofi", "gpa": 3.2}
new_student = create_student(**info)
print(new_student)
Output{'name': 'Kofi', 'gpa': 3.2, 'major': 'Undeclared'}

Keys must be hashable

Dictionary keys have to be immutable — strings, numbers, and tuples work. Lists don't, because they can change after being used as a key.

lookup = {}
lookup[(40.7, -74.0)] = "New York"   # tuple key: fine
lookup["NYC"] = "New York"           # string key: fine
lookup[[1, 2]] = "oops"              # list key: crashes
OutputTraceback (most recent call last): TypeError: unhashable type: 'list'

Why dictionaries are fast

Looking up a value by key in a dictionary takes roughly the same amount of time no matter how big the dictionary is — O(1) on average. Searching for something in a plain list means checking items one by one — O(n), slower as the list grows. This is part of why database drivers hand you rows as dictionaries: fast lookup by column name.

JSON and dictionaries are practically the same shape

JSON (JavaScript Object Notation) is the format almost every web API speaks. Python's json module converts between a JSON string and a dictionary in one call — because a JSON "object" and a Python dict already look nearly identical.

import json

student = {"name": "Kofi", "gpa": 3.2, "major": "Undeclared"}

as_json = json.dumps(student)   # dict -> JSON string
print(as_json)
print(type(as_json))

back_to_dict = json.loads(as_json)  # JSON string -> dict
print(back_to_dict)
print(type(back_to_dict))
Output{"name": "Kofi", "gpa": 3.2, "major": "Undeclared"} <class 'str'> {'name': 'Kofi', 'gpa': 3.2, 'major': 'Undeclared'} <class 'dict'>
Keep this in mind too: the Airtable section relies entirely on this — every response from its API arrives as JSON, and Python turns it straight into a dict.

Real World · Part A

Without a database: a library tracker in plain Python

Before reaching for a real database, here's the same idea small tools start with: a list of dictionaries held entirely in memory, acting as a stand-in for a "Books" table.

The in-memory "table"

library = []

def add_book(book_id, title, author, available=True):
    library.append({
        "id": book_id,
        "title": title,
        "author": author,
        "available": available
    })

add_book(1, "Dune", "Frank Herbert")
add_book(2, "1984", "George Orwell")

print(library)
Output[{'id': 1, 'title': 'Dune', 'author': 'Frank Herbert', 'available': True}, {'id': 2, 'title': '1984', 'author': 'George Orwell', 'available': True}]

Finding and updating a record

Without a database, "querying" just means looping through the list and checking each dictionary.

def find_book(book_id):
    for book in library:
        if book["id"] == book_id:
            return book
    return None

def checkout_book(book_id):
    book = find_book(book_id)
    if book and book["available"]:
        book["available"] = False
        return f"You checked out {book['title']}"
    return "Book not available"

print(checkout_book(1))
print(library)
OutputYou checked out Dune [{'id': 1, 'title': 'Dune', 'author': 'Frank Herbert', 'available': False}, {'id': 2, 'title': '1984', 'author': 'George Orwell', 'available': True}]

Where this approach breaks down

This works fine for a script or a classroom demo, but it has real limits:

• Nothing is saved. The moment the program ends, library is gone — there's no file, no server, nothing to reopen tomorrow.
• No sharing. Two people running the program at the same time each get their own private copy; neither sees the other's changes.
• Doesn't scale. Looping through a list to find one record is fine for a dozen books, painfully slow for a million.

The fix isn't a new data structure — it's the same dictionaries and the same shape, just handed to us by something that remembers: a real database. The next two sections show two very different kinds of "real": a cloud API (Airtable) and a traditional relational server (MS SQL Server).

Real World · Part B

With a database: Airtable

Airtable is a cloud spreadsheet that behaves like a lightweight database, reachable over a web API. Every response it sends back is JSON — and as you saw in the advanced section, json.loads() turns JSON straight into a Python dictionary. That's the whole trick to this section.

Reading records

The requests library fetches the data; .json() parses it into a dict for you automatically.

import requests

BASE_ID = "appXXXXXXXXXXXXXX"
TABLE_NAME = "Books"
API_KEY = "your_personal_access_token"

headers = {"Authorization": f"Bearer {API_KEY}"}
url = f"https://api.airtable.com/v0/{BASE_ID}/{TABLE_NAME}"

response = requests.get(url, headers=headers)
data = response.json()   # <-- already a dict, no extra work needed
print(type(data))
print(data)
Output<class 'dict'> {'records': [{'id': 'recA1B2C3D4E5F6', 'createdTime': '2026-01-15T10:00:00.000Z', 'fields': {'Title': 'Dune', 'Author': 'Frank Herbert', 'Available': True}}, {'id': 'recG7H8I9J0K1L2', 'createdTime': '2026-01-15T10:01:00.000Z', 'fields': {'Title': '1984', 'Author': 'George Orwell', 'Available': True}}]}
Notice the shape: a dict with a "records" key holding a list of dicts — and each of those has its own nested "fields" dict. Nested dictionaries from Level 2, right where you'd expect them.

Reshaping the response into plain records

Airtable's raw format has some extra wrapping (id, createdTime, fields). It's common to flatten it into simpler dictionaries your own code can work with.

books = []
for record in data["records"]:
    books.append({
        "id": record["id"],
        "title": record["fields"]["Title"],
        "author": record["fields"]["Author"],
        "available": record["fields"].get("Available", True)
    })

print(books)
Output[{'id': 'recA1B2C3D4E5F6', 'title': 'Dune', 'author': 'Frank Herbert', 'available': True}, {'id': 'recG7H8I9J0K1L2', 'title': '1984', 'author': 'George Orwell', 'available': True}]

This should look familiar — it's the exact same list-of-dictionaries shape as the in-memory library list from the previous section. Same shape, except now it's backed by a server that remembers it after your program ends.

Creating a record

To create a record, you build the dictionary yourself and send it — the dict becomes the request body.

new_book = {
    "fields": {
        "Title": "Brave New World",
        "Author": "Aldous Huxley",
        "Available": True
    }
}

response = requests.post(url, headers=headers, json=new_book)
created = response.json()
print(created["fields"])
Output{'Title': 'Brave New World', 'Author': 'Aldous Huxley', 'Available': True}

Updating and deleting

record_id = "recA1B2C3D4E5F6"
record_url = f"{url}/{record_id}"

# update just the fields you name -- PATCH only touches what you send
requests.patch(record_url, headers=headers, json={"fields": {"Available": False}})

# delete removes the whole record
requests.delete(record_url, headers=headers)

Real World · Part C

With a database: MS SQL Server

MS SQL Server speaks SQL, not JSON. When you run a query with pyodbc, each row comes back as a plain tuple — not a dictionary. So this time, instead of a library doing the conversion for you like Airtable's .json() did, you build the dict yourself. And you already know exactly how: zip().

Connecting and querying

import pyodbc

conn = pyodbc.connect(
    "DRIVER={ODBC Driver 17 for SQL Server};"
    "SERVER=localhost;"
    "DATABASE=Library;"
    "UID=your_username;"
    "PWD=your_password;"
)
cursor = conn.cursor()
cursor.execute("SELECT BookID, Title, Author, Available FROM Books")

raw_rows = cursor.fetchall()
print(raw_rows[0])
print(type(raw_rows[0]))
Output(1, 'Dune', 'Frank Herbert', True) <class 'pyodbc.Row'>

A row prints like a tuple, and you access fields by position (row[0], row[1]…) unless you turn it into a dictionary yourself.

Turning rows into dictionaries

cursor.description holds the column names from your query. Zip those names together with each row's values, and dict() does the rest — the exact pattern from the advanced section.

columns = [column[0] for column in cursor.description]
print(columns)

books = []
for row in cursor.fetchall():
    books.append(dict(zip(columns, row)))

print(books)
Output['BookID', 'Title', 'Author', 'Available'] [{'BookID': 1, 'Title': 'Dune', 'Author': 'Frank Herbert', 'Available': True}, {'BookID': 2, 'Title': '1984', 'Author': 'George Orwell', 'Available': True}]
Same shape again — a list of dictionaries, one per book. Whether the data came from a Python list, Airtable's JSON, or a SQL Server table, it always lands in your code the same way: as dictionaries.

Inserting and updating

Use ? placeholders with the actual values, never string-formatting them directly into the SQL — that avoids SQL injection.

new_book = {"Title": "Brave New World", "Author": "Aldous Huxley", "Available": 1}

cursor.execute(
    "INSERT INTO Books (Title, Author, Available) VALUES (?, ?, ?)",
    new_book["Title"], new_book["Author"], new_book["Available"]
)
conn.commit()

# mark BookID 1 as checked out
cursor.execute("UPDATE Books SET Available = ? WHERE BookID = ?", 0, 1)
conn.commit()
