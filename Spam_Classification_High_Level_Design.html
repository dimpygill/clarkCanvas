How an engineering team translates approved requirements into a buildable software design.

Status: Proposed high-level architecture — pending review. Algorithm selection and internal implementation are intentionally deferred.

1. Purpose and design boundaries

The system classifies one English text message as Spam or Not Spam. This design is the bridge between project requirements and implementation.

Industry connection: A design document answers “How will we build it?” and provides a shared reference for developers, reviewers, and testers. Design decisions remain proposals until reviewed.

In scope: labeled CSV data; Python; text processing text features; Multinomial classification model; held-out evaluation; a simple one-message demo interface; input length of 1–1,000 characters; results labeled Spam or Not Spam.

Out of scope: Gmail integration, deleting messages, batch uploads, production deployment, language detection/translation, and multilingual classification.

2. High-level architecture

The system has two separate workflows: one prepares a model from labeled data; the other uses that trained model to classify new messages.

False positive: a legitimate message is incorrectly flagged as spam. False negative: spam is incorrectly labeled as not spam. Both must be discussed; a high accuracy score alone does not establish suitability.

8. Risks, decisions, and next stage

  • Class imbalanceExample: A dataset has 950 normal messages and 50 spam messages. A model that predicts 'not spam' for everything gets 95% accuracy but catches zero spam. Review class counts, spam precision, recall, and F1—not accuracy alone.: evaluate precision/recall and class counts, not accuracy alone.
  • Dataset mismatchExample: The model is trained on formal English SMS messages, but real users submit messages with slang, emojis, abbreviations, or unfamiliar writing styles. Predictions may be less reliable because real inputs differ from training data.: messages unlike the training data may be misclassified; document limitations.
  • LeakageExample: 'Congratulations, you won a free iPhone' accidentally appears in both training and test sets. The model may recognize a message it already saw, making evaluation results look better than performance on genuinely new messages. Keep test data separate and check duplicates before splitting.: use keeping test data out of model training.
  • Artifact compatibilityExample: A model saved using one Python or machine-learning library version may fail to load with another. A virtual environment helps isolate dependencies, but versions must also be documented or pinned; Python version and sometimes operating system matter too. Only load trusted model files.: pin dependencies and load only a trusted model artifact.
  • English-only scopeThis prototype is designed and evaluated for English messages only. Example: 'आपने इनाम जीता है' is outside the tested scope. It might receive a prediction, but its reliability has not been established. Automatic translation or language detection is not included.: no automatic language detection; predictions on other languages are not validated.

Design review checklist

  1. Does every agreed requirement map to a component or behavior?
  2. Are the training and prediction workflows separated correctly?
  3. Are invalid input and missing-model scenarios specified?
  4. Does evaluation avoid test-data leakage and include error analysis?
  5. Are exclusions and limitations clear to reviewers?
Industry milestone: Reviewers may approve, request changes, or reject the proposed design. Only after resolving significant design issues should the team treat it as the implementation baseline. This document does not claim a completed review or sign-off.
